# iCeSugar Pro FPGA Architecture

This document summarizes the ECP5 display/audio architecture used by the
iCeSugar Pro side of the receiver.

The final bitstream is `icesugar_pro/src/top.sv`. It receives TLV IQ samples
from PlutoSky, renders the live spectrum/waterfall UI, demodulates FM audio, and
drives the LCD and I2S DAC.

## Top-Level Dataflow

The easiest way to read `top.sv` is as four mostly separate paths that meet at
the display:

1. PlutoSky sends IQ samples into the FPGA.
2. The FPGA turns those samples into spectrum/waterfall pixels and FM audio.
3. The Pico sends UI state into the FPGA.
4. The LCD scan-out combines stored framebuffer pixels with live UI overlays.

The key split is this:

- **SDRAM holds persistent pixels**, mainly the waterfall/framebuffer content.
- **The pixel shader draws live overlays**, such as text, buttons, touch cursor,
  and spectrum bars, while the LCD is scanning out.
- **Audio does not go through SDRAM**; it is demodulated and buffered directly
  into the I2S output path.

```text
                         +---------------- iCeSugar Pro ECP5 ----------------+
                         |                                                    |
PlutoSky IQ TLV stream ->| SPI/TLV RX -> IQ samples -> FFT -> spectrum bins   |
                         |                         |                          |
                         |                         +-> waterfall row -> SDRAM |
                         |                         |                          |
                         |                         +-> FM demod -> I2S audio  |
                         |                                                    |
Pico UI state frames --->| UI RX -> status/control registers -> pixel shader  |
                         |                |                                   |
                         |                +-> JP5 MISO command backchannel    |
                         |                                                    |
SDRAM framebuffer ------>| scan_out -> line_cache -> pixel shader -> LCD RGB  |
                         +----------------------------------------------------+
```

### 1. PlutoSky IQ Input

PlutoSky is the SPI master on JP5. It sends TLV packets into the ECP5:

```text
spi_frame_rx -> tlv_demux -> tlv_iq_sink
```

`spi_frame_rx` receives raw SPI bytes. `tlv_demux` identifies packet type.
`tlv_iq_sink` converts `TLV_IQ` payload bytes into signed `{I, Q}` sample words.

### 2. Spectrum And Waterfall

Each IQ sample also feeds the display DSP path:

```text
IQ -> spectrum_zoom_decimator -> fft256 -> spectrum_bin_ram
```

`spectrum_bin_ram` stores the latest 256 FFT magnitudes. The pixel shader reads
those bins directly when drawing the live spectrum overlay.

The same FFT output is expanded into a waterfall row. That row is written into
the SDRAM framebuffer through the compositor path:

```text
FFT magnitudes -> waterfall row writer -> compositor -> sdram_arb -> sdram_ctrl
```

### 3. FM Audio

The audio path is independent of the LCD framebuffer:

```text
IQ -> fm_demod -> audio_volume -> audio_fifo -> i2s_tx
```

`fm_demod` produces PCM audio. `audio_volume` applies volume/mute from the Pico
UI state. `audio_fifo` smooths timing before `i2s_tx` drives the DAC pins.

### 4. Pico UI And Backchannel

The Pico sends shared `0xA5` UI frames into the ECP5. Two parsers consume that
same SPI stream:

```text
spi_ui_cmd_rx -> control_regs -> spi_backchannel
ui_wire_rx    -> ui_status_prepare -> pixel_shader_top
```

`ui_wire_rx` stores fields needed by the display, such as frequency, mode,
volume, touch position, active button, and status text. `ui_status_prepare`
formats those fields into text and compact shader inputs.

`spi_ui_cmd_rx` extracts radio/audio commands. Volume and mute are used locally
on the ECP5. Mode and frequency changes are sent back to PlutoSky through
`spi_backchannel` on JP5 MISO.

### 5. LCD Scan-Out

The LCD is fed continuously. For each line:

```text
SDRAM framebuffer -> scan_out -> line_cache -> pixel_shader_top -> RGB LCD
```

`scan_out` reads framebuffer rows from SDRAM before the LCD needs them.
`line_cache` stores a few rows in EBR so the pixel clock can read them without
waiting on SDRAM. `pixel_shader_top` combines the framebuffer pixel with live UI
overlays and sends the final RGB565 pixel to the LCD pins.

## Clock Domains

| Domain | Purpose |
|---|---|
| System/SDRAM clock | SPI receive, FFT, SDRAM controller, compositor, FM demod |
| Pixel clock | LCD timing and shader scan-out |
| I2S clocking | Audio serial output generated by `i2s_tx` |

Clock crossings are handled with asynchronous FIFOs and the line cache. The LCD
shader reads a prepared line from EBR while the SDRAM side fills future lines.

## Display Timing

The LCD is an 800x480 RGB-parallel panel using RGB565 pixels. `scan_timing.sv`
generates HSYNC, VSYNC, DE, and active `(x, y)` coordinates. `pixel_shader_top`
combines framebuffer pixels with live UI/status overlays at scan-out time.

The final UI uses:

- Frequency and span text
- Mode labels
- Volume/mute state
- Touch crosshair and active button highlight
- Spectrum bins from the FPGA FFT
- Optional RDS/status text supplied by the Pico path

## SDRAM Display Path

The display path uses the onboard 32 MB SDRAM through:

| Module | Role |
|---|---|
| `sdram_ctrl` | Low-level SDRAM command sequencer |
| `sdram_arb` | Shared access arbitration |
| `scan_out` | Reads framebuffer rows into EBR line cache |
| `line_cache` | Multi-line EBR buffer between SDRAM and pixel clock |
| `compositor` | Writes waterfall/framebuffer updates |

### Half-Page Framebuffer Layout

The SDRAM part is used conservatively: image bursts stay within columns
`0..255` of an SDRAM row. Logical pixels are still addressed as a flat
`800x480` RGB565 framebuffer, but physical SDRAM placement uses only half of
each 512-word SDRAM row.

For logical word `W = y * 800 + x`:

```text
sdram_row = W >> 8
sdram_col = W & 255
byte_addr = FB_BASE + ((sdram_row << 10) | (sdram_col << 1))
```

This means one 800-pixel LCD row spans up to four SDRAM rows. The scan-out and
compositor paths must use the same mapping.

## Memory Map

| Region | Base | Size | Use |
|---|---:|---:|---|
| `FB_FRONT` | `0x0000_0000` | 1.5 MB | Active framebuffer, half-page layout |
| `FB_BACK` | `0x0018_0000` | 1.5 MB | Reserved back buffer |
| `WATERFALL_HISTORY` | `0x0030_0000` | 512 KB | Waterfall scrollback |
| `GOES_FULL_IMAGE` | `0x0038_0000` | 512 KB | Reserved satellite-image region |
| `ADSB_BASEMAP` | `0x0040_0000` | 768 KB | Reserved ADS-B basemap region |
| `AUDIO_RING` | `0x004C_0000` | 256 KB | Reserved audio history region |
| `SCRATCH` | `0x0050_0000` | Rest of SDRAM | Future use |

Only the regions used by the final FM display/audio path are active in
`top.sv`. The remaining regions document reserved space for protocol extensions.

## EBR Resources

The design keeps hard real-time scan-out and small lookup tables in EBR:

| Resource | Use |
|---|---|
| Line cache | Holds rows fetched from SDRAM for pixel-clock scan-out |
| Font ROM | Status/UI text glyphs |
| Sprite ROM | Button and UI sprite assets |
| Spectrum bin RAM | 256 FFT magnitude bins for the shader |
| FIFOs | SPI IQ buffering and audio buffering |

Large image data and waterfall history live in SDRAM instead of EBR.

## FM Signal Path

`TLV_IQ` samples are written into an IQ FIFO. The final bitstream fans IQ into:

- FFT and spectrum display
- Waterfall row generation
- FM demodulation

The FM demod path produces signed PCM samples, applies ECP5-local volume/mute,
buffers audio, and sends it out through `i2s_tx`.

`spectrum_zoom_decimator.sv` changes the FFT input rate for narrower requested
spans while keeping 256 display bins. It is a practical demo zoom block, not a
full DDC/channelizer.

## Pixel Shader And C Model

The live overlay is implemented in both C and SystemVerilog:

| Implementation | Path |
|---|---|
| C reference | `icesugar_pro/model/src/pixel_shader.c` |
| RTL shader | `icesugar_pro/src/pixel_shader.sv` |
| RTL wrapper | `icesugar_pro/src/pixel_shader_top.sv` |

The Verilator checks in `icesugar_pro/sim/` compare RTL shader/ROM behavior
against the C model.

## Diagnostics

Hardware diagnostic top modules live in `icesugar_pro/tests/` and are built by
explicit Makefile targets:

| Target | Purpose |
|---|---|
| `make prog_lcd_test` | LCD wiring |
| `make prog_tlv_link_test` | JP5 TLV receive path |
| `make prog_fm_audio_test` | Minimal FM audio path |
| `make prog_sdram_test` | SDRAM controller check |

These diagnostics are intentionally separate from the final `top.sv` build.
